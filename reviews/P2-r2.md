## Findings

### HB-P2-r2-C1 (correctness, minor): a non-root runner cannot read the audit log, and no contract says how it gets one

- Evidence: `contracts/run.md:26` now says the runner never runs as uid 0. `contracts/truth.md:7` says the collector reads "The text of `/var/log/audit/audit.log` (or a copy)", and no contract says who makes the copy or how. auditd's default `log_group = root` with mode 0600 (`auditd.conf(5)`) leaves the file unreadable for the run account. The install line in `contracts/audit.rules.template:3` covers rules only.
- Why minor: P3b and P3c read the log as text from fixtures, so no lane is blocked. The gap is in the P4 runner and the box setup.
- Fix (P4, Request for integration): name the mechanism in `contracts/run.md`. One option is `log_group` set to a group the run account is in, which Tony sets on the box. Another is a root-owned `ausearch --raw` step limited to the run's time window, which writes `R/audit.log`. Then point `truth.md:7` at that file.

### HB-P2-r2-E1 (eval validity, minor): a bare IP word in a command does not name the address

- Evidence: `contracts/monitor.md:65` counts a command word only when it is a URL or `<address>:<port>`. So `nc 192.0.2.10 443`, `ssh 192.0.2.10` and `ping 192.0.2.10` name nothing. The fixture comment on sequence 5 (`fixtures/monitor/connect.expected.json`, `echo 192.0.2.100`) depends on this rule. For the monitor under test, this undercounts `named`, so the egress table could understate what the monitor captures.
- Why minor: table 3 is secondary and never folded into the headline (`SPEC.md:32`). The rule is stated and tested, not hidden. Its direction is known: it can only lower `named`.
- Fix (P4 or P5): either count a word that is exactly an IP literal (IPv4 dotted, or IPv6 accepted by `net.isIP`), with a red test for `nc <addr> <port>`, or state the undercount beside the `egress` rows.

### HB-P2-r2-S1 (security, minor): the root guard that has a test is the weaker of the two

- Evidence: `renderRules` refusing `uid: 0` (P3b-rules-root) only stops a rule file filtered on `euid=0`. What stops a scenario from changing the box's `/etc/hosts` is the runner refusing euid 0 (`contracts/run.md:26`). That is P4 code, and no test pins it yet. The template's own install line (`contracts/audit.rules.template:3`, `sed ... $(id -u <run-user>)`) also skips `renderRules`.
- Why minor: the contract states the runner rule, and section 3's P4 exit gate requires a security review with no open S finding above low. Nothing runs on the box before P4.
- Fix (P4): a cross-lane test that starts the runner with euid 0 (or a stubbed `process.geteuid`) and expects it to exit before it creates `R`. P4's security review checks for it.
