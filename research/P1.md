## 1. Product surface: Asymptote Labs

- **Company.** $5.5M seed led by Tower Research Ventures, with Lytical Ventures, 1984 Ventures and South Park Commons (F1, F2, F3). It says it is "initially focused on securing AI agents at runtime through real-time detection and response" (F1).
- **Beacon (open source, MIT).** `LICENSE:1-3` in B: "MIT License, Copyright (c) 2026 Asymptote Labs". It captures sessions from 20+ harnesses into one OpenTelemetry-based data model (F1; B `README.md`). The repo description now leads with "cross-harness, self-improving memory layer" (GitHub API, `description`), but its topics include `agent-security` and `detection-engineering`, and F1 names security as the first market.
- **Collection is the harness's own report.** B `docs/runtimes/index.mdx:20-50`: each harness is collected through its hooks, plugin, OTLP export, or a poll of its session files. The "Telemetry coverage" column states what each harness exposes. It is declared coverage, not measured coverage.
- **No kernel feed.** B `docs/platforms/linux-deployment-profile.mdx:15`: "eBPF / audit subsystem | Not used". Line 17: "ptrace, process injection | Not used".
- **Detections.** B `rules/`: 87 `*.rule.yaml` files in 10 categories, written in CEL over normalized events, each with inline tests (for example `rules/agent-control/sandbox-escape-attempt.rule.yaml`). There are 11 in `sensitive-edit/`. Several are about writes outside a project: `shell-login-dotfile-modified`, `ssh-authorized-keys-modified`, `autostart-unit-file-installed`, `direnv-envrc-modified`, `etc-hosts-modified`.
- **beacon-sandbox, the live-agent test tool.**
  - B `beacon-sandbox/README.md:4`: it "runs a real Claude Code session inside it".
  - `README.md:19`: it needs "an Anthropic API key with credit".
  - `README.md:109`: the image is "Linux, a pinned Claude Code, and your Beacon build".
  - `image/image.go:32`: `DefaultClaudeVersion = "2.1.220"`.
  - `credentials/credentials.go:1`: "resolves the Anthropic API key the sandboxed agent needs".
  - `scenario/scenario.go:174-176`: `BlockEgress` is "only useful for scenarios that need no model call, since Claude Code needs the API".
  - The sandbox runs on Modal or on a GitHub Actions Windows runner.
- **What beacon-sandbox says it cannot show.** In its Limitations section, B `beacon-sandbox/README.md` says it "confirms the thing it planted was recorded rather than proving nothing else was missed."
- **Airlock** (https://github.com/Asymptote-Labs/airlock) is a second open-source product: a context broker that controls what data reaches an agent (`README.md:1-5`). It has no bearing on capture rates.

## 3. Competitor comparison

The two closest competitors, chosen because both monitor coding-agent CLIs on developer machines and publish how they capture:

| | Beacon (Asymptote) | Endor Labs Coding Agent Governance | Quint |
|---|---|---|---|
| Capture path | Harness hooks, OTLP, session-file poll (B `docs/runtimes/index.mdx`) | Harness hooks (E: "Hook problems never block developers. If a hook cannot run ... The event stays missing") | OS level on macOS, beside the agent's own report (Q: "Agents report what they did. Quint records what actually executed, out of band at the OS level") |
| Harnesses | 20+ | Claude Code, Cursor, Codex, Copilot, Cortex Code. Some marked limited (E: "Cursor CLI: Shell command hooks fire reliably. Prompt, file edit, and stop events do not") | Claude Code end to end. Codex and Gemini CLI through their OTel. Cursor CLI as a process (Q) |
| Open source | Yes, MIT | No | No |
| Linux | Yes | Yes | No, "Quint runs on macOS today" (Q) |
| Published, measured capture rate per harness with a denominator | No | No. Gaps are stated as prose caveats (E). | No. Per-harness statements are qualitative: "Measured so far, each on one of Quint's own Macs" (Q) |

A kernel-level vendor, BeyondTrust (BT: "Enforcement is applied on the endpoint, at the kernel and network level"), shows the market already sees the gap between what a hook reports and what the OS sees. Nobody publishes the size of that gap per harness.

**Where the build sits.** It is not a monitor. It is an open benchmark that measures any hook-based monitor against a kernel record, per harness. It runs first against Beacon on Linux, the platform Quint does not cover, and adds a keyless model path that beacon-sandbox lacks. Its output is a number none of the three publishes.

## 4. Candidates, scored (BUILD_OUTLINE.md section 2)

Score 1 to 5, one sentence of evidence each. Ties go to "Not a clone".

### A. Capture-vs-kernel matrix for Beacon, with a keyless scripted model (the brief's build)

Real harness CLIs are driven by a scripted, keyless model server. Each scenario makes the agent write outside its workspace in three ways: the native edit tool, a shell command, or a script the agent runs. auditd records every write. The build reports, per harness, the share of those writes that Beacon's runtime log names. It also reports which Beacon rules fire, per harness. A keyless provider for beacon-sandbox is staged under `upstream/` and not sent.

### Pick

**A, with 23.** B and C tie at 18. Both lose to A on "Their customers feel it" and on "Not a clone". Later phases do not reopen this pick (section 2). Reopening it is a Tony gate.

### Headline number

**Per-harness capture rate of out-of-workspace file writes.** For one harness, the denominator is the out-of-workspace writes that auditd records from that harness's process tree during the frozen scenario set. The numerator is how many of those writes Beacon's runtime log names by path. It is reported per harness, with the denominator, as a five-run band, and never as a composite. The alternative headline, network egress, is a secondary table. Under `srt`, egress goes through a proxy, so per-connection kernel records are ambiguous. File writes have one clean kernel record per path. This is an agent's call, logged in DECISIONS.md.
